1. Introducción y objetivos

La práctica empaqueta los componentes de Subsonic Festival y describe cómo ejecutarlos juntos. La implementación toma como referencia la Práctica 2 integrada en main (2b868e1). Esta edición documenta los cambios de Andrea y los archivos disponibles del resto del equipo.

2. Arquitectura general

El navegador recibe la SPA de Nginx. El mismo servidor dirige las peticiones de /api/ a las cinco API. Cada API tiene su propia instancia PostgreSQL. Proveedores consulta autenticación para las operaciones protegidas y eventos para validar solicitudes vinculadas a un festival.

3. Tecnologías

Docker y Compose gestionan las imágenes, contenedores, redes y volúmenes. Las API usan FastAPI sobre Uvicorn, con SQLAlchemy y Psycopg para PostgreSQL. React, TypeScript y Vite generan los archivos estáticos que sirve Nginx.

4.6 Proveedores · Andrea

La API gestiona perfiles de proveedores, servicios externos, espacios alquilables, solicitudes y presupuestos. Su Dockerfile usa python:3.14-slim y fija /app/provider-service/generated como directorio de trabajo. Instala requirements.txt antes de copiar el código para reutilizar la capa de dependencias. FastAPI y Pydantic sirven y validan la API, Uvicorn ejecuta el servidor, SQLAlchemy y psycopg[binary] acceden a la base de datos y HTTPX realiza las consultas entre servicios.

PYTHONPATH apunta a src, PYTHONDONTWRITEBYTECODE=1 desactiva la escritura de cachés de bytecode y PYTHONUNBUFFERED=1 facilita la lectura inmediata de logs. La lista de inclusión del Dockerfile limita la copia a requisitos y código Python del servicio. Las pruebas y el seed se ejecutan por fuera de la imagen de la API.

El lifespan llama a Base.metadata.create_all(bind=engine). GET /health comprueba el proceso HTTP. GET /ready ejecuta SELECT 1 y devuelve 503 ante un error de PostgreSQL. La sonda del contenedor invoca esa misma ruta en 127.0.0.1:8000 con la biblioteca estándar. Las llamadas reales de negocio a autenticación y eventos se comprueban por separado.

9. Construcción y despliegue

Desde la raíz del repositorio, construir la imagen y comprobar sus dependencias instaladas.

docker build -f provider-service/generated/Dockerfile -t subsonic-provider:test .
docker run --rm subsonic-provider:test python -m pip check

Tras integrar el Compose definitivo y configurar el entorno local, ejecutar docker compose up -d --build --wait. Consultar el estado con docker compose ps -a y los logs con docker compose logs provider. El frontend se abre en http://localhost:5173.

11. Problemas encontrados y soluciones aplicadas

El Dockerfile previo usaba Python 3.10, copiaba el contexto completo y ejecutaba las pruebas durante la construcción. La nueva imagen instala las dependencias de ejecución, copia el árbol de código y declara el mando de Uvicorn y la sonda. Las dependencias de pruebas siguen disponibles para un entorno separado.

El motor Linux de Docker Desktop estaba detenido al iniciar la revisión. Para la prueba se arrancó el motor y se usó el proyecto aislado subsonic-andrea. Una sobreescritura temporal de Compose fijó image: subsonic-provider:test y build: !reset null solo para provider. Así se conservó la imagen de seed del Compose de referencia.
